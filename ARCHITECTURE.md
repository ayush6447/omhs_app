# OMHS Architecture

## System
```
 Teensy (Board 1)  ──UART text lines──▶  ESP32-C3 (Board 5)  ──BLE NUS──▶  Flutter app
   cuff, LEDs,                              forwards lines                 (Android / iOS)
   optical sensing                          unchanged
 ◀──────────── CMD,START / CMD,STOP / CMD,STATUS / OTA,… ─────────────────
```
Board 5 is a transparent bridge, so the app parses exactly what the Teensy
prints. The firmware owns safety (max cuff pressure, max inflation time).

### State (provider + ChangeNotifier)
| Provider | Owns | Persisted in |
|---|---|---|
| `AppSettings` | theme mode, chol unit, body units, setup done, reminder | shared_preferences |
| `ProfileStore` | profiles, active profile, photos | shared_preferences + app docs |
| `DeviceService` | link status, phase, pressure, currents, progress, result, firmware | last device ID (BLE) |
| `ReadingsStore` | all readings, filtered to active profile | `readings.json` |
| `NotificationService` (plain `Provider`) | reminder schedule, alert notifications | OS scheduler |
| `AccountService` | signed-in Firebase user | Firebase Auth |
| `CloudSync` | sync status, last sync time | Firestore + per-user hashes in shared_preferences |

`FirmwareUpdater` is not global: the Firmware screen owns one for as long as
it is open.

### Data flow for one measurement
1. User taps Start → `DeviceService.start()` → `sendLine("CMD,START")`.
2. BLE notifications are split on `\n` → `handleLine()` → `parseLine()` →
   `DeviceEvent` → state fields updated → `notifyListeners()` → Measure screen
   rebuilds.
3. `RESULT,…` creates a `Reading` (stamped with peak pressure, LED currents,
   firmware) and emits it on `DeviceService.results`.
4. `ReadingsStore` (subscribed to `results`) tags it with the active profile
   and saves (chained writes, temp file + rename).
5. Dashboard / History / TrendChart rebuild from `ReadingsStore`.
6. `trendAlerts()` runs on the active profile's readings: shown on Measure and
   Dashboard; if the app is in the background, `main.dart` posts the top
   alert as a notification.

## Trend alerts (`trend_alerts.dart`)
Checked on the newest reading only, most important first:
- **Weak signal** (quality < 0.6): the only alert, since the number isn't trusted.
- **High**: in the high band for the person's age.
- **Worse band**: higher band than the previous trusted reading.
- **Rising**: ≥ 20 mg/dL *and* ≥ 10 % above the mean of the previous 3 trusted
  readings from the last 90 days.

## Reminders
`ReminderSchedule` (daily, or weekly on a weekday, at a time) is saved in
`AppSettings`. `NotificationService.applyReminder` schedules one repeating
notification (`zonedSchedule` + `matchDateTimeComponents`, inexact so no alarm
permission) and is called on every change and at launch (time-zone changes).
Permission is asked only when the user turns reminders on.

## Cloud (Firebase project `omhs-1ec50`)
Optional: if `Firebase.initializeApp` fails the app runs as before and the
Account section is hidden.

- **Sign-in:** Google Sign-In (`google_sign_in` 7, Credential Manager on
  Android) -> `GoogleAuthProvider.credential(idToken)` -> Firebase Auth.
  Android needs the signing SHA-1 registered in Firebase (debug key is
  registered; release currently uses the debug key too). iOS uses
  `iosClientId` and the `REVERSED_CLIENT_ID` URL scheme in `Info.plist`.
- **Data:** `users/{uid}` (FCM tokens), `users/{uid}/profiles/{id}` (profile
  JSON, photo inlined as base64 if <= 700 KB; no Firebase Storage, which
  needs the paid plan), `users/{uid}/readings/{id}` (reading JSON). Demo
  readings (`demo-*`) are never uploaded.
- **Sync:** full sync on sign-in, app resume and "Sync now": read both
  collections, compare each document's hash with the hash stored at the
  last sync (`planSync`) to tell additions, edits and deletions on either
  side apart; this phone wins when both edited the same document. Local
  changes are pushed 3 s later without reading (`planPush`). Offline writes
  are queued by Firestore (status "syncs when online"). On a fresh phone the
  empty starter profile is replaced by the account's profiles.
- **Rules:** `firestore.rules` — a user can only read/write `users/{uid}/**`
  for their own uid. Deploy: `firebase deploy --only firestore:rules`.
- **Delete cloud copy:** removes the user's documents and signs out; data on
  the phone stays.
- **Push (FCM):** every install subscribes to topic `all`; send from the
  Firebase console (Messaging -> campaign -> topic `all`). Foreground
  messages are shown via the `messages` notification channel. iOS needs an
  APNs key uploaded in Firebase and the Push Notifications capability.
- Database location: `nam5` (US).

## Firmware updates (OTA)
Draft protocol on the same text link; the firmware side is not written yet.
```
app  OTA,BEGIN,<B1|B5>,<size>,<crc32 hex>   device  OTA,READY[,<max chunk>]
app  OTA,DATA,<offset>,<base64>             device  OTA,ACK,<next offset>
     … one chunk in flight; ACK may ask for an earlier offset (resend) …
app  OTA,END                                device  OTA,OK | OTA,FAIL,<msg>
app  OTA,ABORT   (cancel; device drops what it received)
```
- Chunk size: as many bytes as fit in one BLE write (`maxLineLength` = MTU − 3),
  capped by the device's `READY` value. Lines longer than one write are split
  and Board 5 must join them up to the newline.
- Timeouts: 30 s for `READY` (flash erase), 5 s per `ACK` with 3 resends,
  60 s for `OK`. Link loss or Cancel fails the update.
- Board 5 handles `B5` itself (ESP32 OTA partition; images must start with
  `0xE9`) and forwards `B1` to the Teensy. Both must verify size + CRC-32
  before switching images, so an interrupted update keeps the old firmware.
- After `OK`: Board 5 restarts (link drops, auto-reconnect, `VER` refreshes);
  for Board 1 the app sends `CMD,STATUS` after 6 s.
- Measuring is blocked while an update runs (`DeviceService.isUpdatingFirmware`).

## Connection lifecycle (BLE)
- `connect()`: try the remembered device ID directly (8 s), fall back to a
  10 s scan for the NUS UUID or a name containing `OMHS`; remember the ID.
- `resume()` on launch and on returning to the foreground: quiet reconnect to
  the remembered device only.
- On a drop: `ReconnectPolicy` retries after 1, 2, 4, 8, 15, 30 s (then every
  30 s), scans every 3rd attempt, gives up after 2 min. Paused in background,
  restarted when Bluetooth turns back on. Only the same device is accepted.
- After every (re)connect the app sends `CMD,STATUS` so it learns the current
  phase and firmware.
- A drop mid-cycle sets `interruptedCycle`; that cycle's result is discarded.
- A `_session` counter cancels stale connect attempts and retry loops.

## Device protocol (draft)
One message per line, comma separated. Unknown lines are ignored.

| Direction | Line | Meaning |
|---|---|---|
| Device → app | `STATE,IDLE\|INFLATE\|HOLD\|MEASURE\|DEFLATE\|DONE` | Cycle phase |
| Device → app | `P,<mmHg>` | Cuff pressure |
| Device → app | `I,<ch1 mA>,<ch2 mA>` | LED currents (ISENSE1/2) |
| Device → app | `PROG,<0..1>` | Cycle progress |
| Device → app | `RESULT,<mg/dL>,<quality 0..1>` | Estimate + signal quality |
| Device → app | `ERR,<message>` | Fault; app shows it and stops |
| Device → app | `VER,<b1 fw>,<b5 fw>` | Firmware versions |
| App → device | `CMD,START` / `CMD,STOP` | Start / stop a cycle (Stop is a request) |
| App → device | `CMD,STATUS` | Firmware should reply with `STATE` and `VER` |
| Both | `OTA,…` | Firmware update, see above |

BLE: service `6E400001-B5A3-F393-E0A9-E50E24DCCA9E`, RX (write)
`6E400002-…`, TX (notify) `6E400003-…`.

## Storage formats
- `readings.json`: array of `Reading.toJson()`. Unreadable file is renamed
  `readings.json.corrupt-<ts>` and kept.
- Backup: JSON `{format: "omhs-backup", version: 1, createdAt, activeProfileId,
  profiles (photo inlined as base64), readings}`; newer versions are rejected;
  restore replaces everything on the device.
- CSV: one row per reading, both units, firmware column.
